# iPad v2 contract: decisions taken and questions for the backend owner

**Status:** the iPad client, in-process mock and fixtures implement the v2 shapes below (branch `ios/v2-migration`). Where [Interface.md](../Interface.md) was silent or ambiguous, the iOS side made the smallest reasonable choice. Each choice is listed here so the backend owner can confirm it or change it. Nothing in `backend/` was changed. The wire examples are the JSON fixtures in [Packages/CacheFlowKit/Tests/CacheFlowKitTests/Fixtures/v2](Packages/CacheFlowKit/Tests/CacheFlowKitTests/Fixtures/v2). A backend contract test can load the same files.

## Questions that block a real integration

1. **Reconnect ordering.** Interface.md says the server sends a state snapshot on connect, then replays from a cursor. The client drops any envelope whose `seq` is not greater than the last one it applied. A snapshot sent first with a fresh `seq` would therefore cause every replayed event to be discarded. The mock sends replayed events with their original `seq` and `"replayed": true`, then a fresh `state`. Is that acceptable? The alternative is a snapshot carrying `seq` equal to the cursor.
2. **Cursor.** Is `GET /v2/sessions/{id}/events?after_seq=N` the right resume parameter? With no cursor, the server sends only a snapshot.
3. **Cancellation channel.** The client cancels with a WSS `cancel_turn {turn_id, request_id}` message. `POST /intent {action:"cancel", turn_id}` is also encodable. Which one is canonical? Should the server always answer with the proposed additive `turn_cancelled` event (payload `{reason}`) as the cancellation boundary?
4. **Check = board upload + intent.** For `check`, `hint`, `explain_step`, `draw` and `show_answer`, the client uploads `POST /board` once per board revision, then sends `POST /intent` with the same `board_revision`. Should `/board` itself produce a stream result (for example `read_back`), or only store the snapshot as the mock does?
5. **Board revision semantics.** The revision counts edits to the student's board: the question box and the working area. Committing tutor ink does not bump it. Every tutor event must echo the revision of the request that produced it, because the iPad commits ink/scenes only on an exact match. Please confirm.
6. **Authentication.** Interface.md requires authenticated HTTPS/WSS but defines no mechanism. The client sends `X-Socrates-Protocol: 2` and no credential yet. The default profiles assume `https://<host>:8443`.

## Shapes the iOS side chose (please confirm or amend)

- **Envelope:** `{"v":2,"type","session_id","seq","board_revision","turn_id"?,"run_id"?,"request_id"?,"replayed"?,"payload":{…}}`. Client messages use `{"v":2,"type","session_id","board_revision","payload":{…}}`.
- **`state`:** `{phase, problem?{text,subject,confirmed,item}, latest_turn_id?, skills[]}`. The client expects a `state` on every phase change, not only on connect. Phases: `idle, reading, confirm, ready, tutoring, student_turn, independent_check, complete`. `item` is `lesson` or `independent_check`.
- **`read_back`:** `{request_id, source: question|board|transcript, text, alternatives[], ambiguous, note?, regions[{line_index?, bbox:[x,y,w,h]}]}`. A question read-back always asks for confirmation; board/transcript read-backs ask only when ambiguous. `read_back_confirm {request_id, accepted, text?}`, where `text` is the student's pick or correction. A confirmed transcript is treated as an `ask`.
- **Typed replies:** `ask` with `text` during the lesson; `quiz_answer` with `text` for the independent transfer item. There is no separate `answer` action.
- **`evidence`:** this adds `label` (`verified | supported_by_source | not_verified`; a missing label is read as `not_verified`), `line_index`, `subject`, `independent`, `highlights[]` and `normalized_step`. `unknown/ambiguous_input` is shown as “Not graded”.
- **`tutor_turn`:** `{move, caption, audio_url?, evidence_ids[], assisted, highlights[]}`. Several `tutor_turn`s may share one `turn_id`; the mock uses this for Show the answer followed by the transfer question. A new `turn_id` supersedes the old turn, and its unfinished audio, ink and scenes are discarded.
- **Ink:** `tutor_ink_preview {ink_id, style: write|highlight|circle, region, strokes[[[x,y]]], formula?}` and `tutor_ink_commit {id}`. `tutor_ink_ack {turn_id, ink_id, placed, reason?}`, with reasons `stale_revision` and `invalid`. After a `stale_revision` nack, the mock re-evaluates and re-issues once with a new `ink_id`.
- **Scenes:** `scene_preview {scene_id, title, region, primitives[{kind, points[], text?}]}` and `scene_commit {id}`. The approved kinds are `axes, plot, point, label, arrow, segment, box, number_line`. Limits are 64 primitives and 1024 points, with every point inside the region. An unknown kind refuses the whole scene (`scene_ack placed:false reason:"invalid"`).
- **`audio_chunk`:** `{chunk_index, audio_url, caption_span (text), final}`. `audio_done {turn_id, chunk_index?}` is sent after each clip or chunk.
- **`skills`:** `{skills:[{skill,label,level,independent_evidence,assisted}]}`.
- **`error`:** `{request_id?, code, message, retryable, latest_board_revision?}`.
- **HTTP:** `POST /v2/sessions {preset_id?, locale}` returns `{session_id, protocol_version, board_revision}`. `/question` is multipart with `board_revision`, `request_id` and either `image` (PNG) or `text`. `/board` is multipart: `meta` JSON `{board_revision, request_id, image_region, lines[]}` plus `image` (PNG ≤ 4 MB, ≤ 40 lines). `/audio` is multipart with `board_revision`, `request_id` and `audio` (WAV), returning `{request_id, transcript, ambiguous}`. `/intent` takes JSON `{action, board_revision, request_id, text?, turn_id?}`. The other endpoints are `GET /summary` returning `{items[{problem,outcome,assisted,independent,evidence_ids}], skills, next_step}`, `DELETE /v2/sessions/{id}`, and `GET /v2/health` returning `{protocol_version, components{name:{ok,revision?,latency_ms?,detail?}}}`. The status-code mapping is: 409 `{latest_board_revision}` → stale, 413 → too large, 426 → upgrade.
- **Preset IDs:** `quad_5_6, quad_7_12, lin_2_3_11, phys_forces_box`.
